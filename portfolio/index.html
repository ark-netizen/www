“영어 공부를 하러 들어가는 대신,
업무가 먼저 나에게 도착하면 어떨까?”

학습 세션이 아니라 ‘가상 회사의 하루’를 설계했습니다.

동료·상사·거래처가 서로 다른 채널과 말투로 연락하고, 사용자는 답장·힌트·외근·리포트·복습·승급을 하나의 업무 흐름 안에서 경험합니다. 게임 모드와 비즈니스 모드는 기능이 다른 서비스가 아니라 같은 학습 구조를 다른 인터페이스로 보여주는 두 표현 방식입니다.

PRODUCT LOGIC

관계별 어투를 제품 구조로 분리

동료는 캐주얼, 상사는 프로페셔널, 거래처는 포멀한 톤으로 상황을 분리했습니다. 단순 회화 생성이 아니라 관계·채널·업무 맥락이 답변 난이도와 표현에 영향을 주도록 설계했습니다.

INTERVENTION

행동 신호로 개입 시점 결정

‘외근 중’을 누르면 실패로 처리하지 않고 30분 뒤 재알림합니다. 반복된 바쁨은 행동 신호로 보고, 학습 압박 대신 동료의 짧은 위로 메시지로 정서적 리텐션을 설계했습니다.

LEARNING LOOP

힌트 사용을 다음 학습 데이터로

한국어 → 단어 → 문장 순서의 힌트를 열게 하고, 어느 단계까지 열었는지 복습 난이도와 리포트에 반영합니다. ‘도움을 받은 기록’ 자체를 학습 신호로 사용합니다.

OPERATIONS

서비스 운영까지 포함한 MVP

출석·연차·직급·승급, 관리자 화면, CS·설문, 알림, 일일 리포트까지 한 제품 안에 구성했습니다. 기능 데모보다 실제 운영 가능한 학습 서비스 구조에 초점을 맞췄습니다.

BACKEND

프론트와 서버 비밀값을 분리

브라우저에는 VITE 환경값만 노출하고, Supabase service role·LLM 키·VAPID private key·cron secret은 Edge Function secret으로 관리합니다. 서버 API는 Supabase Edge Functions에서 동작합니다.

DEPLOYMENT

한 번의 push로 두 레이어 배포

GitHub Actions에서 프론트 Vite build와 Supabase Edge Function 배포를 함께 처리합니다. 예약 알림 dispatch는 pg_cron으로 실행되도록 구성했습니다.

“팬 반응을 모으는 데서 끝나지 않고,
판단에 필요한 맥락까지 바로 읽을 수는 없을까?”

수집 도구와 해석 도구를 한 흐름으로 묶었습니다.

X·YouTube·Instagram에서 계정·게시물·댓글을 구분해 수집하고, 저장된 데이터를 감성·키워드·트렌드·관계망으로 살펴본 뒤 AI에게 질문할 수 있도록 구성했습니다. 분석 결과가 다시 콘텐츠·캠페인 판단으로 이어지는 것을 목표로 했습니다.

CAPTURE

브라우저 탐색 중 바로 수집

페이지를 보다가 필요한 반응만 선택해 수집하도록 확장프로그램 흐름을 설계했습니다. 플랫폼별 데이터를 하나의 대시보드로 가져오되 원본 유형을 유지합니다.

ANALYSIS

단일 감성 점수보다 여러 관점 제공

긍정·부정·중립 분포, 키워드, 시간 변화, 동시출현 관계망을 함께 보여줘 특정 반응 하나에 과도하게 의존하지 않도록 했습니다.

AI LAYER

선택한 데이터에 질문하는 구조

수집된 데이터 범위를 먼저 선택한 뒤 AI가 그 범위 안에서 요약·맥락 해석·다음 액션을 보조하도록 구성했습니다. 원본 데이터와 생성 결과를 분리해 볼 수 있게 했습니다.

DATA

정제 규칙을 운영 화면으로

동의어·불용어·임시 보정 규칙을 데이터 워크스페이스에서 관리해 분석 품질을 반복적으로 다듬을 수 있도록 했습니다.

FRONTEND

분석 성격에 따라 시각화 분리

분포·추이는 Recharts, 관계 구조는 force graph 계열을 사용해 데이터 종류별로 시각화 방식을 다르게 선택했습니다.

Python 기반 수집 라이브러리와 NLP 처리를 FastAPI 서버에 두고, 프론트는 결과 탐색과 사용자 의사결정에 집중하도록 역할을 나눴습니다.

“모든 감정을 꼭 분석해야 할까?
잠시 나와 떨어뜨려 두는 경험은 어떨까?”

감정을 삭제하는 대신 ‘흘려두는’ 인터랙션을 만들었습니다.

모래 위에 마음을 쓰면 파도가 글씨를 지우고 해파리가 가져갑니다. 이후 ‘나의 바다’에서 그 마음이 계속 여행하고 있다는 소식을 받는 구조로, 사용자가 감정을 붙들고 반복해서 분석하지 않아도 시간의 흐름을 느끼게 설계했습니다.

좋아하는 아티스트에서 받은 감정과 팬 경험을 출발점으로, 엔터테인먼트 경험이 새로운 서비스 경험으로 확장될 수 있는지 실험한 프로젝트입니다.
INTERACTION

텍스트 입력과 Canvas 장면을 연결

사용자의 손글씨·텍스트 입력이 모래, 파도, 해파리 애니메이션으로 이어지도록 상태 전환을 구성했습니다. 완료 카드가 캐릭터 대사보다 먼저 뜨지 않도록 타이밍도 분리했습니다.

PERFORMANCE

상태별 FPS를 다르게 운용

기본 30fps, 입력 중 15fps, 주요 파도·캐릭터 애니메이션은 50fps로 동적으로 조절해 모바일 렌더링 부하와 체감 품질을 균형 맞췄습니다.

CANVAS

정적 배경을 캐시해 재계산 최소화

하늘·모래 질감·별 등 변하지 않는 요소는 별도 Canvas에 캐시하고, 매 프레임 다시 그리지 않도록 했습니다.

MOBILE

DPR·키보드 resize 비용 제어

모바일 Canvas DPR 상한을 1.5로 제한하고, 키보드가 열릴 때 발생하는 resize 동안 Canvas 재할당을 막아 입력 시 끊김을 줄였습니다.

ASSET

오디오·이미지는 실제 필요 시점에 로드

첫 터치에서 오디오 버퍼를 만들지 않고 효과음 사용 시점으로 초기화를 지연했습니다. 도착 사진도 800px JPEG로 최적화하고 도착 화면이 열릴 때 로드합니다.

DISTRIBUTION

Apps in Toss 패키징 흐름 대응

@apps-in-toss/web-framework 기반으로 개발하고 .ait 패키지를 생성해 콘솔 배포 흐름에 맞췄습니다. 실제 서비스 화면과 마케팅 이벤트 측정까지 연결했습니다.

RUNTIMETypeScript · Vite 7 · HTML Canvas · Web Audio
PLATFORM@apps-in-toss/web-framework 2.10.8 · .ait build pipeline
DATAFirebase 연동 지점 · 로컬 상태 및 서비스 이벤트
PERFDynamic FPS · static canvas cache · DPR cap · lazy asset initialization

“공연을 보는 순간뿐 아니라,
그곳으로 향하는 과정도 팬 경험 아닐까?”

PUBLIC SCOPE

공연 전후의 오프라인 경험을 연결

공연을 중심으로 동행·이동·현장 정보를 한곳에서 다루는 팬 경험 서비스를 개발 중입니다. 구체적인 연결 방식과 매칭 규칙은 공개 범위를 제한하고 있습니다.

AUTH

X OAuth를 서버 사이드로 분리

X API key/secret과 session secret을 서버 환경값으로 관리하고, 인증 callback과 session API를 Vercel serverless layer로 분리했습니다.

CONCERT DATA

KOPIS 공연 데이터를 서비스 흐름에 연결

공연 목록을 별도 API에서 갱신하도록 구성해 팬이 실제 공연 단위로 탐색할 수 있는 기반을 만들고 있습니다.

LIFECYCLE

임시 연결 데이터의 수명 관리

Vercel Cron으로 만료된 연결 데이터를 정리하는 maintenance route를 두고, 생성·신청·결정·종료의 라이프사이클을 API 단위로 나눴습니다.

QA

변경이 잦은 흐름은 회귀 테스트로 보호

인증, 공연 빈 상태, 생성 플로우, 연결 유지, 지도 설정, UI 줄바꿈 등 실제로 깨지기 쉬운 흐름을 node test suite로 고정했습니다.

PRIVACY

공개 정보와 민감 연결 정보를 분리

공개 공연 정보와 인증·비공개 연결 정보를 같은 레이어에서 다루지 않도록 API 경계를 나누고, 세부 제품 규칙은 포트폴리오에서도 의도적으로 공개하지 않습니다.

BACKGROUND

Entertainment
→ Product

콘텐츠를 만들고 유통하던 경험, 팬덤 반응을 직접 보던 경험, 디지털 마케팅에서 데이터를 보던 경험이 지금의 제품 설계 방식으로 이어졌습니다.

팬이 콘텐츠를 만나는 순간을 보고,
그 경험을 새로운 서비스와 사업으로 확장합니다.

KBS미디어에서 음악사업을 운영하며 제작·유통·계약·정산·팬 이벤트까지 End-to-End로 경험했고, 퍼포먼스 마케팅에서는 광고 반응과 전환 데이터를 실무에서 다뤘습니다.

이후에는 직접 React·TypeScript·Python·Supabase·LLM을 사용해 아이디어를 제품으로 만들고 있습니다. 엔지니어링 자체보다, 기술을 어디에 어떻게 붙여야 실제 사용자 경험과 사업 구조가 달라지는지에 더 관심이 있습니다.

그래서 포트폴리오의 네 프로젝트도 도메인은 달라도 같은 방식으로 시작합니다. 사용자가 실제로 겪는 불편이나 감정의 맥락을 먼저 보고, 그 다음에 필요한 기술을 고릅니다.
